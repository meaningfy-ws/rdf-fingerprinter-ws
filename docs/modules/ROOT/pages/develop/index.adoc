= Developer runbook
:description: How RDF Fingerprinter WS is developed: the method, where code goes, the tools, how work is shaped, verified, committed and documented.

This runbook describes how this repository is developed, for people and agents. `AGENTS.md` at the
repository root is the short form that agents load. It has four pages:

* this one: the method, the structure, the tools and the conventions;
* xref:develop/rdf-fingerprinter.adoc[Building on rdf-fingerprinter]: what the library does for the
  service, and what to do when it falls short;
* xref:develop/agents.adoc[Working with agents]: what is specific here when agents deliver the
  work (the method itself is skillery's `epic-delivery` skill);
* xref:develop/testing.adoc[Testing checklist]: the rules every test follows.

== Common questions

*Where do I start a new feature?*::
In a shaping session: an EPIC in `openspec/changes/<id>/`. Code comes after the PLAN passes the
clarity gate. See <<work>>.

*The library does not do what I need. What now?*::
Report it in `rdf-fingerprinter` as a GitHub issue; never work around it here. See
xref:develop/rdf-fingerprinter.adoc#strict[Building on rdf-fingerprinter].

*Which checks must pass before a PR?*::
See <<before-pr>>.

*Who checks that we built the right thing?*::
The developer, at fixed points of the lifecycle. Agents verify; people validate. See <<vv>>.

== Who does the work

One developer leads a team of AI agents. The developer sets direction, answers questions and
decides; a *lead* agent runs each session, briefs *member* agents for bounded tasks, checks their
work, commits and keeps the spine. In practice:

* *A session replaces the sprint.* A shaping session produces EPICs; an epic session delivers one,
  stage by stage, each stage one PR. The EPIC's appetite (Shape Up) replaces the sprint length.
* *The spine replaces the tracker.* EPIC, PLAN and tasks live in `openspec/changes/<id>/`; a task's
  checkbox in `tasks.md` is the ticket; the commit that closes it cites it.
* *Questions replace meetings.* An agent that needs a decision asks the developer, with options and
  a recommendation; the answer is recorded in the change.
* *Reports are claims.* Nothing an agent reports counts until the lead has re-run the checks and
  read the diff.

== How we code

* *Clean architecture* (Cosmic Python), *SOLID*, *KISS* and *YAGNI*: the smallest change that fully
  solves the task.
* *Test first.* A test precedes the code it tests (red, green, refactor).
* *Hard fail.* A function never returns `None` to signal failure; it raises a specific error.
* *Comments say why*, only where the code cannot.
* *The library does the fingerprinting.* See
  xref:develop/rdf-fingerprinter.adoc[Building on rdf-fingerprinter].

[#work]
== How work is organised

Work is planned before it is coded, in the OpenSpec spine:

* the *EPIC* is `openspec/changes/<id>/proposal.md` (appetite, why, solution, rabbit holes, no-gos);
* the *PLAN* is `design.md` + `tasks.md`, scored by the clarity gate (≥ 9/10) before the first task;
* the *requirements* are spec deltas, `specs/<cap>/spec.md` (SHALL, with scenarios), merged into
  `openspec/specs/` when the change is archived.

Library work is planned in the library's own spine; an EPIC here that needs it names the library
change or issue.

[#vv]
== Verification and validation

_How do we know we built the right thing, and built it right?_

* *Verification* asks "did we build it right?": code against its tests and spec scenarios, the
  structure against the layering. It is mostly mechanical, and agents do most of it.
* *Validation* asks "did we build the right thing?": the scenarios against what the developer
  wants, the delivered feature against the EPIC's success measure. It always ends with the
  developer; an agent prepares the evidence and can recommend.

[cols="2,3,3",options="header"]
|===
|Artefact |Validated by |Verified by
|EPIC |The developer agrees the why, the appetite and the success measure |The clarity gate (≥ 9/10) on EPIC and PLAN
|Spec scenarios and Gherkin |The developer's *scenario sign-off*, before a stage's build |The *traceability check*: every scenario has a test, every feature test names its scenario
|Code |The *acceptance demo*, before the PR of a stage that delivers or changes a use case |The tests and gates, the five-lens review, the verifier
|Docs |The *cold reader*: a fresh agent carries out the page |The snippets run; every page is in the navigation (`make check-docs`)
|===

Evidence lives with the change, in `openspec/changes/<id>/evidence/` (`spike-<topic>.md`,
`acceptance-<stage>.md`), and is archived with it.

== Documentation

* The docs are this Antora component, in `docs/modules/ROOT/`; every page is in the navigation
  (`make check-docs`). Install the toolchain once with `make install-antora`; build with
  `make build-docs`, preview with `make preview-docs`.
* Each page opens with the questions it answers.
* Each stage updates the pages it changed.

== Source control

* Branch off `develop` (`feature/<change-id>`, `fix/…`, `docs/…`); never commit to `develop` or
  `main` directly. PRs target `develop` and merge only on green CI; `main` receives releases.
* One task per commit, one repository per commit. Conventional Commits, imperative, no trailing
  period; the body gives the *why*, the *what* and the *trace* (`Refs: <change-id> <task>`).
* No AI attribution in commits or PRs.

== Reporting a bug

* *A bug in this service*: a GitHub issue in `meaningfy-ws/rdf-fingerprinter-ws`, labelled `bug`,
  saying what happens and how to reproduce it.
* *A bug or a missing capability in the library*: a GitHub issue there, in the shape on
  xref:develop/rdf-fingerprinter.adoc#issue[Building on rdf-fingerprinter]. Never a workaround here.
* A bug found while working on a task is fixed test-first: a failing test, then the fix.

[#before-pr]
== Before a PR

* The gates pass: `make check-all`, and `make check-docs` when `docs/` changed. From stage 2 of the
  library-upgrade EPIC, also the container tests when adapters or infra changed.
* No workaround of the library; every library issue met is filed and linked from `design.md`.
* The stage's scenarios were signed off and the traceability check is clean; for a use-case stage,
  the acceptance demo is recorded in `evidence/`.
* Each commit cites its change and task; the PR targets `develop`.
